## 4. Поэтапная диагностика

### 4.1. Проверка SSH master и локального форварда

```bash
ssh -S ~/.claude-wrapper/tunnel.sock -O check root@claude-proxy
# Master running (pid=5892)

lsof -iTCP -sTCP:LISTEN -P | grep :8888
# ssh 5892 ... TCP localhost:8888 (LISTEN)
```

**Вывод:** SSH master жив, порт слушает.

### 4.2. Прямое обращение к прокси через форвард

```bash
curl -v --max-time 5 --proxy http://127.0.0.1:8888 https://api.anthropic.com/
```

Результат: `Connection timed out after 5006 milliseconds` (curl exit 28).  
Прокси возвращает `000` в логах watchdog, но на самом деле TCP-соединение устанавливается.

### 4.3. Ручной CONNECT к прокси

```bash
( echo "CONNECT api.anthropic.com:443 HTTP/1.1"; echo "Host: api.anthropic.com:443"; echo "Proxy-Connection: keep-alive"; echo "" ) | nc -w 5 127.0.0.1 8888
# HTTP/1.1 200 Connection established
```

Прокси успешно согласует CONNECT-туннель, но дальше данные не идут — TLS Client Hello уходит в никуда.

### 4.4. Проверка «мусорного» запроса

```bash
curl -v http://127.0.0.1:8888/
# HTTP/1.1 400 Bad Request
```

Прокси парсит HTTP и отвечает. Значит, процесс прокси **не завис окончательно** — он принимает соединения и читает заголовки.

### 4.5. Создание свежего SSH master (исключение «зависшего» старого)

```bash
ssh -o ControlMaster=no -o ControlPath=none -N -L 127.0.0.1:18888:127.0.0.1:18080 root@claude-proxy
# порт 18888 слушает

curl --max-time 10 --proxy http://127.0.0.1:18888 https://api.anthropic.com/
# 000 10.0s (таймаут)
```

**Вывод:** проблема воспроизводится на чистом SSH-соединении. Старый master не виноват.

### 4.6. Проверка HTTP (без HTTPS/CONNECT)

```bash
curl --max-time 10 --proxy http://127.0.0.1:18888 http://httpbin.org/get
# 000 10.0s (таймаут)
```

Даже обычный HTTP-прокси-запрос зависает. Проблема не в TLS handshake.

### 4.7. Попытка exec/shell/sftp на ru-vds

```bash
ssh -o ControlMaster=no -o ControlPath=none root@claude-proxy "echo OK"
# зависание на 60+ секунд

echo "ls /" | sftp root@claude-proxy
# зависание
```

SSH transport layer (аутентификация) работает, но открытие `session` channel (exec, shell, sftp) таймаутится. На этом этапе это выглядело как исчерпание ресурсов на сервере (невозможность `fork`).

### 4.8. Сетевая доступность ru-vds

```bash
ping -c 3 193.124.129.94
# 0% packet loss, ~9 ms RTT
```

Сервер по сети доступен. VPN (Cisco AnyConnect) на клиенте в статусе `Disconnected`, но для доступа к этому IP он не требуется.

## 5. Ложные следы

| Гипотеза | Почему отвергнута |
|----------|-------------------|
| «Завис» старый SSH master | Свежее соединение показывает ту же картину |
| Прокси упал совсем | Прокси отвечает `400 Bad Request` на некорректные запросы |
| Проблема в сети клиент → ru-vds | Ping ~9 мс, SSH transport работает, форвард слушает |
| Нехватка ресурсов на ru-vds (fork) | Возможно, частично верно (exec таймаутится), но не объясняет, почему прокси именно молчит на валидные запросы |
| Прокси блокирует конкретный хост | Любой хост (`api.anthropic.com`, `google.com`, `httpbin.org`) ведёт себя одинаково |

## 6. Вердикт

**Корневая причина:** упал (или «завис») **туннель между ru-vds и Hetzner**.

Прокси на ru-vds жив и принимает клиентские соединения, но не может установить исходящее соединение к upstream (Hetzner). Прокси либо:
- пытается достучаться до Hetzner и ждёт бесконечно (нет таймаута upstream в конфиге),
- или туннельный интерфейс/маршрут «висит» мёртвым (TCP-соединение к Hetzнеру разорвано, но ядро не отправило RST).

Зависание SSH exec/shell на ru-vds — скорее всего **сопутствующий симптом** (sshd тоже пытается форкнуться в условиях нагрузки от тысячи висящих прокси-соединений, или это отдельная проблема конфигурации `sshd`).

## 7. Архитектурные проблемы, выявленные инцидентом

1. **Единая точка отказа без мониторинга:**  
   Watchdog (`bin/tunnel-watchdog`) следит только за звеном `macOS → ru-vds`. О **туннеле `ru-vds → Hetzner`** он ничего не знает и не может отреагировать.

2. **Прокси не возвращает ошибку при отвале upstream:**  
   Вместо `502 Bad Gateway` или быстрого `connection refused` клиент получает бесконечный таймаут. Это делает диагностику сложнее и ломает retry-логику `claude`.

3. **Отсутствие автозапуска / self-healing на ru-vds:**  
   Если туннель между ru-vds и Hetzner — это ручной `ssh -D` в `screen`, то после ребута ru-vds его не будет. Даже hard reboot не гарантирует восстановление сервиса.

4. **Нет разделения healthcheck'ов:**  
   Сейчас один прокси-URL (`https://api.anthropic.com/`) проверяет сразу три звена: SSH master, прокси, Hetzner-туннель, интернет. При падении любого из них диагностика затруднена.

5. **SSH exec/shell заблокирован на ru-vds:**  
   Отсутствие возможности выполнить команду на ru-vds через SSH сильно усложняет удалённую диагностику и починку.

## 8. Что нужно сделать прямо сейчас

1. **Восстановить туннель `ru-vds → Hetzner`.**
   - Вариант А: зайти через консоль RuVDS (VNC/serial) и проверить `systemctl status` туннельного сервиса.
   - Вариант Б: hard reboot ru-vds через панель (риск: сервисы могут не автостартовать).

3. **Проверить, что `claude` на macOS ожил** (лог watchdog должен вернуться к `OK`).

## 9. Рекомендации по доработке схемы (чтобы не повторялось)

### 9.1. Оформить туннель ru-vds → Hetzner как systemd-сервис

```ini
# /etc/systemd/system/ruvds-to-hetzner.service
[Unit]
Description=SSH tunnel ru-vds -> Hetzner
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
Restart=always
RestartSec=10
ExecStart=/usr/bin/ssh -NT -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -D 127.0.0.1:1080 hetzner-jump
# или для WG: ExecStart=/usr/bin/wg-quick up wg0

[Install]
WantedBy=multi-user.target
```

Затем:
```bash
systemctl enable --now ruvds-to-hetzner
```

### 9.2. Настроить tinyproxy/microsocks с таймаутом upstream

Если используется tinyproxy — добавить в конфиг:
```conf
Timeout 10
ConnectPort 443
ConnectPort 80
```

Чтобы при недоступности Hetzner клиент получал `504 Gateway Timeout` вместо бесконечного висяка.

### 9.3. Добавить healthcheck на ru-vds

Простой скрипт на ru-vds (через cron или systemd timer), который каждую минуту:
1. Проверяет, пингуется ли Hetzner через туннель.
2. Проверяет, отвечает ли `api.anthropic.com` через локальный прокси.
3. При FAIL — рестартит туннельный сервис (`systemctl restart ruvds-to-hetzner`).

### 9.4. Разделить healthcheck на клиенте (macOS)

В `bin/tunnel-watchdog` можно добавить логику:
- Проверка A: `ssh -O check` (жив ли master).
- Проверка B: `curl` через прокси на **внешний хост**, не зависящий от Hetzner (например, если Hetzner — единственный маршрут, то это сложно, но можно проверить ответ DNS или ping).
- Проверка C: `curl` на `api.anthropic.com`.

Если A=OK, а C=FAIL — watchdog может попытаться `ssh -O exit` + recreate master (как описано в спеке `2026-05-15-tunnel-self-healing.md`). **Но в данном инциденте это не помогло бы** — проблема за SSH master.

### 9.5. Рассмотреть вариант без промежуточного ru-vds

Если Hetzner — это финальный прокси, имеет смысл подумать о прямом SSH-туннеле `macOS → Hetzner` (если политика безопасности позволяет). Это уберёт одно звено и одну точку отказа.

Альтернатива: поднять прокси **на Hetzner** и сделать SSH-туннель `macOS → Hetzner` напрямую, а ru-vds использовать только как fallback.

### 9.6. Вернуть SSH shell/exec на ru-vds (если возможно)

Отсутствие shell сильно усложняет аварийное восстановление. Можно рассмотреть:
- Отдельного пользователя с ограниченным shell (`rbash`, `git-shell`, или `ForceCommand` только для конкретных задач).
- Или хотя бы возможность `ssh root@claude-proxy "/usr/local/bin/emergency-restart"`.

## 10. Связь со спеком self-healing

Файл `docs/superpowers/specs/2026-05-15-tunnel-self-healing.md` описывает улучшение watchdog для случая «master alive, но forward channel застрял». Этот инцидент показывает, что **даже с self-healing на клиенте** проблема может лежать глубже — за пределами SSH master. Поэтому в спек стоит добавить:

- Параграф о **границах ответственности watchdog**: он лечит только `macOS → ru-vds`, не `ru-vds → upstream`.
- Рекомендацию добавить **раздельный healthcheck** (п. 9.4) чтобы отличать «упал master» от «упал upstream».
- Упоминание, что `claude-tunnel status` должен показывать не только состояние SSH, но и **время отклика прокси** (если оно резко возросло — раннее предупреждение).

## 11. Errata и уточнения (дополнено 2026-05-18, пост-разбор)

Разделы 1–10 выше написаны в 10:55, в разгар инцидента, **до доступа к ru-vds** — часть формулировок там предположительная. Ниже — что подтвердилось по факту после диагностики на сервере и анализа логов.

### 11.1. Уточнённая архитектура

- Прокси на ru-vds — это **Xray** (HTTP-inbound `127.0.0.1:18080`), не tinyproxy/microsocks.
- Звено ru-vds → Hetzner — **WireGuard**, интерфейс **`wg-tunnel`** (IP `10.88.88.2`, endpoint Hetzner `95.217.128.117:51820`). Xray уходит наружу через `sendThrough: 10.88.88.2` → `ip rule` → таблица 100 → `wg-tunnel`.
- На сервере есть **второй** WG-интерфейс — `wg0` (`10.77.77.1`), несвязанный VLESS-VPN. К инциденту отношения не имеет. В п. 9.1 `wg-quick up wg0` упомянут как пример **ошибочно** — правильный юнит туннеля называется `wg-quick@wg-tunnel`.

### 11.2. Подтверждённая корневая причина

Интерфейс `wg-tunnel` пропал — ядро удалило его при внешнем сетевом событии VDSina. `wg-quick@wg-tunnel.service` имеет `Type=oneshot` + `RemainAfterExit=yes`: systemd считал сервис живым (`active (exited)`) и не пересоздал интерфейс. Xray продолжал слушать, но `sendThrough: 10.88.88.2` указывал на несуществующий интерфейс → бесконечные таймауты. Вердикт п. 6 («упал туннель ru-vds → Hetzner») по сути верен.

### 11.3. Реальная шкала восстановления

Клиентский `~/.claude-wrapper/tunnel.log` показывает непрерывный `FAIL` с **10:33:58 до 13:00:49** — простой **2 ч 27 мин**. Восстановлено ручным `wg-quick up wg-tunnel` около 13:00:4x в SSH-сессии (через systemd-юнит туннель не перезапускался — в journald следа нет).

**Правильная команда восстановления на будущее:** `systemctl restart wg-quick@wg-tunnel` (не `wg0`).

### 11.4. Повторный провал в тот же день

15:47–16:14 (~27 мин) — ещё один провал. В journald за это окно событий нет: интерфейс не падал, `xray.service` был жив. «Тихий» отказ WG-сессии или upstream Hetzner; восстановился сам. Причина не установлена — за этим теперь следит логгер (см. 11.6).

### 11.5. Сопутствующая находка — конфликт двух Xray

На сервере параллельно крутилась панель `x-ui` со своим встроенным xray-core, конфликтовавшим с `xray.service` по портам (`11111/443/62789`) — crash-loop каждые ~8 с. 2026-05-18 `x-ui.service` остановлен и `disabled`. VPN семьи (`:443`) и claude (`:18080`) обслуживает единственный `xray.service` (`-c /etc/xray-config.json`); список VLESS-клиентов ведётся в `/etc/xray-config.json`.

- Установлен серверный логгер стабильности: `/usr/local/bin/wg-tunnel-stat.sh` (read-only) + root cron `* * * * *` → `/var/log/wg-tunnel-stat.log`. Исходник в репо: `extras/server/wg-tunnel-stat.sh`.
